# AI Export v2: Compact / Diagnostic и сверка идентичности Сбера

24 сентября 2026 · версия приложения 1.0.50+51.

## Результат и оставшееся ограничение

Два режима одного `qesto.ai-export.v2`: `compact` («Лёгкий», по умолчанию)
и `diagnostic` («Полный»). Одна кнопка сохранения, один immutable canonical
snapshot, одинаковые операции, деньги, privacy, периоды и HMAC-идентификаторы.

На локальной копии предоставленных данных подтверждены и исправлены 11 пар
старых/новых записей. 234 → 223 операции. Шестая группа пока требует точного
сопоставления source ID; считать всю задачу дедупликации полностью закрытой нельзя.

## Доказанная первопричина

Гипотеза про unresolved → resolved описывала внешний симптом, но реальная
хронология обратная:

1. Старые записи появились 2–7 сентября на определённом счёте.
2. Старый canonical/provider ID имел вид `sber-sber-transaction-…`: хеш строки
   DOM, банковского ID, даты и округлённой суммы в рублях.
3. 10 сентября повторный импорт использовал новые scoped identities:
   `sber-operation-v2` / `sber-provider-v1` на основе connection + bank operation ID.
   Параллельно источник перестал назначать общий счёт без подтверждения — появились
   корректные временные `sber-unassigned-*` accounts.
4. Переходная совместимость по fingerprint не сработала: формат изменился,
   в том числе рубли → копейки. Сопоставление по экономическим признакам
   принимало только 1:1, намеренно пропуская повторные одинаковые покупки.
5. Для одного `bankWeb` источника fuzzy merge запрещён. Новые provider IDs
   не совпали со старыми, поэтому группы 2:2 и 3:3 стали отдельными canonical rows.
6. Экспорт ошибочно называл наличие любого provider ID `confirmed_unique`.
   Проверка неоднозначностей учитывала разные source types, но не смену версии
   идентичности внутри одного bankWeb источника.

То есть жёсткое сравнение accountId не было основной причиной: виртуальные
счета уже допускались reconciler-ом. Основная потеря — связь поколений source ID.

Исследованы ровно 26 указанных записей, их candidates, SourceEvidence и
ingestion records. Для первых пяти групп использованы ранее сохранённые локальные
строки банковской страницы: каждая строка независимо воспроизводит старый
fingerprint и новый scoped provider ID. Исходные персональные данные, ключи,
номера счетов и сырые банковские ID в репозиторий не включены.

Последняя строка **не означает четыре реальных платежа**: система сохраняет
неоднозначные записи и предупреждение до точного связывания. Два реальных перевода
нельзя склеить в один. Следующая синхронизация с охватом 7 сентября сможет применить
тот же identity bridge, если исходная строка воспроизводит старый fingerprint.
Если представление строки изменилось, потребуется сохранённый HTML/явная сверка.

Подтверждённый лишний учёт первых пяти групп: **4 314 ₽**, не предварительные 4 340 ₽.
Валовые outflow по периоду: 108 891,46 → 104 577,46 RUB; inflow: 102 107,00 RUB,
без изменений. Это суммы направлений операций, не обещание соответствия текущему
балансу и не отдельный расчёт cash flow с исключением внутренних переводов.
Остатки счетов не изменялись. Осталось 65 операций с unresolved account.

## Изменения в коде

- `sber_extractors.dart`: строит legacy IDs из той же source row до потери
  исходного текста; сохраняет совместимость округлённого и точного формата.
- `sber_connector_models.dart`: передаёт эти adapter-only ID через выбор счёта.
- `synoball/reconciliation/bank_web_identity_upgrade.dart`: проверяет scope,
  денежные факты, evidence, конфликтные claims и объединяет **доказанные** идентичности
  в staged Synoball state до импорта. Сохраняет старый canonical ID, объединяет
  evidence, перенаправляет candidate/recurring references, пишет audit/event.
- `budget_controller.dart`: применяет bridge в атомарном staged import; защищает
  операции, связанные с целями, инвестициями и долгами, от удаления их ID.
- `synoball_core.dart`: снимает устаревший тег unresolved, когда canonical account
  уже определён; неизвестный счёт не заменяет известный при повторном наблюдении.
- `bank_web_identity_quality.dart`: отдельная диагностика неоднозначной смены
  поколения ID. **Ничего не объединяет и не удаляет**.
- `canonical_snapshot.dart`: использует диагностику Synoball и сообщает
  `source_identified`, а не недоказанное `confirmed_unique`.
- `ai_export_models.dart`, `ai_export_v2.dart`, `ai_export_dialog.dart`: detailLevel,
  компактная проекция того же документа, выбор режима, новая dataQuality semantics.

### Защита от ошибочного объединения

Недостаточно совпадения даты, суммы и продавца. Нужны два воспроизводимых
идентификатора одной исходной строки и совместимые source scope/evidence.
Разные подтверждённые счета, разные подключения, конфликтующие provider claims,
удалённые записи, конфликтующие ручные правки или защищённые внешние связи
блокируют автоматический merge. Ручная категория сохраняемого canonical остаётся
авторитетной. Исторические payloads и события не переписываются.

Повторные одинаковые платежи различаются банковскими operation ID; regression
проверяет именно 3 → 3, не 3 → 6 и не 3 → 1. Повторный импорт после исправления
сохраняет количество и IDs. Экспорт не фильтрует операции по name/date/amount.

## Compact / Diagnostic

Укороченный синтетический пример одной обычной операции. ID здесь условные.

Лёгкий:

```json
{
  "id": "txn_example", "accountId": "acc_example", "categoryId": "cat_example",
  "occurredDate": "2026-08-18", "name": "Продукты",
  "amount": {"value": "449.95", "currency": "RUB"},
  "type": "expense", "direction": "outflow",
  "cashFlowTreatment": "externalOutflow", "confidence": 0.94
}
```

Полный содержит те же финансовые поля плюс:

```json
{
  "canonical": true, "status": "posted", "accountResolution": "resolved",
  "occurredAt": null, "timePrecision": "date",
  "provenance": {"sourceTypes": ["bank_web"], "evidenceCount": 1, "merged": false},
  "deduplication": {"status": "source_identified", "groupId": null, "confidence": null},
  "categoryAssignment": {"source": "rule", "confidence": 0.94},
  "confidence": {"overall": 0.94, "category": 0.94},
  "userEdited": false, "userEditedFields": []
}
```

Compact оставляет transfer/refund relationships, неясный счёт/дату, сомнительную
дедупликацию, низкую category confidence и ручные изменения. Не выводит `dup_*`
group IDs. Diagnostic сохраняет безопасный HMAC group ID, связывающий неоднозначные
строки. Известные кредитные/брокерские поля сохраняются; неизвестные не выдумываются.
Баланс без даты фиксации не становится «свежим».

Период 04.08–24.09.2026, открытые названия операций и счетов, UTF-8,
`JsonEncoder.withIndent('  ')`, без завершающего перевода строки:

| Файл | Операций | Байт |
|---|---:|---:|
| Исходный v2 | 234 | 293 468 |
| Compact после исправления | 223 | 152 077 |
| Diagnostic после исправления | 223 | 281 385 |

Compact меньше Diagnostic примерно на 46%. UI показывает реальные количества,
но не выдуманную оценку размера. В обоих режимах проверены прежние pseudonymous
IDs всех сохранившихся canonical transactions.

## Data Quality

Фактический результат локального повторного экспорта:

```json
{
  "historyCompleteness": "not_verified",
  "balancesCompleteness": "partial",
  "balanceFreshness": "not_verified",
  "hasUnresolvedAccounts": true,
  "hasPossibleDuplicates": true,
  "deduplicationProcessing": "complete",
  "possibleDuplicateGroups": 1
}
```

Processing complete означает выполненную проверку, а не гарантию отсутствия
дублей. Старое `deduplicationCompleteness` удалено из v2. `historyCompleteness`
находится только в dataQuality; v1 не менялся.
