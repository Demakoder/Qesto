# Ручная классификация Qesto — 1.0.52+53

Дата: 26.09.2026. Протокол: Repository Analysis → Architecture Decision →
Implementation → Tests → Regression Review → Final Report.

## Existing architecture

- Категория уже была стабильным ID: `BudgetTransaction.categoryId` — проекция
  `CanonicalTransaction.effectiveCategory` в Synoball. Приоритет ручного выбора
  обеспечивался `userCategoryOverride` и `user-field:category`.
- Системный каталог находился в `budget_categories.dart`; пользователь мог
  переоформить его через `BudgetCategoryCustomization`, но не создать категорию.
- `EnrichmentEngine` уже нормализовал продавцов и формировал merchant ID.
  Постоянных пользовательских правил и справочника пользовательских тегов не было.
- Поле `tags` уже использовалось импортом для служебной информации. Удаление
  операции уже работало через Synoball-корзину и подавление повторного импорта.
- Общий журнал desktop/mobile — `DesktopTransactionsPage`; подробности — его
  drawer и прежний мобильный `TransactionDetailsScreen`.

## Architecture decision / Data model

Не создано второй базы операций или таблицы назначений категорий. Категория
по-прежнему хранится в canonical transaction; UI и экспорт читают существующие
проекции. `ClassificationSettings` в профиле содержит только пользовательский
каталог, определения тегов, merchant rules и перенаправления объединённых ID.

Новые категории и теги получают ID через существующий `SynoballIdFactory`
с последовательностью, а не только по времени: быстрые создания не сталкиваются.
Системный ID не меняется при переименовании; shortName тоже обновляется, чтобы
новое имя было видно в Обзоре, фильтрах и списках, а не только в менеджере.
Типы доходных/расходных категорий и новая иерархия не вводились.

## Manual override

Приоритет: явный `userCategoryOverride` → пользовательское правило → текущая
автоклассификация → исходная категория/fallback. Даже выбор той же категории
явно закрепляет её. Смена только заметки больше не создаёт случайный category
override. Ручная категория нового расхода и ручной выбор при добавлении чека
передаются в тот же pipeline, поэтому правило продавца их не перебивает.

Повторный импорт добавляет evidence, не отменяя ручной выбор. Устранён обход
этого приоритета старым слоем совместимости категорий Сбера в read model.

## Category rules

Правило хранит ID, entity, нормализованную identity продавца, отображаемое имя,
направление потока и целевой category ID. Оно применяется в существующем
`EnrichmentEngine`; политика передаётся и во временный SynoballCore импорта
выписок/банковской истории. Android-уведомления, SMS, чеки, OCR и голос используют
тот же механизм. Смена правила не перебивает индивидуальный manual override.

Правила видны в редакторе категории. Можно изменить целевую категорию либо
удалить правило. Удаление прекращает его действие; ручные категории сохраняются,
автоматические могут обновиться при последующей обработке. Это не команда
отмены прошлых массовых ручных исправлений.

## Bulk changes

Три области: одна операция / подходящая существующая история / история + правило
на будущее. Перед выполнением показывается число затрагиваемых операций.
Историческая массовая правка — явное ручное решение, в том числе для операций,
ранее отнесённых вручную к другой категории. UI предупреждает об этом.

Совпадение — точная identity существующего merchant normalizer + entity +
направление. Новый произвольный поиск по `contains` не добавлялся. Неизвестный
продавец и общие заглушки «Операция», «Покупка», «Перевод» не позволяют создать
массовое правило. Удалённые операции не входят в обычную массовую правку.

## Categories

Создание, название, цвет, иконка из существующего набора; поиск и недавние
категории в selector. Менеджер показывает число операций за всё время и суммы
за месяц профиля через существующий CashFlowCalculationService, отдельно для
каждой валюты. Из редактора открывается уже существующий журнал с фильтром.

Пустую пользовательскую категорию можно удалить. При наличии связей требуется
перенос. Объединение переносит canonical references, корзину, правила, будущие
планы и суммирует бюджеты одинакового периода; общий бюджет периода не меняется.
Операции, суммы, даты и банковские балансы не удаляются. Для старых Sber-записей
учитывается также исправленная категория, которую пользователь видит в UI.

Перенаправления ID сохраняются для будущих импортов, pending candidates и undo
snapshots. Системная категория скрывается, но остаётся в базовом каталоге;
её можно восстановить. Восстановление не переносит уже объединённые операции
обратно. Перед объединением об этом явно сообщается.

## Tags

Определение тега: стабильный ID, имя, цвет. Связь many-to-many использует
существующее canonical поле `tags` с отдельным namespace `user-label:<id>`.
Служебные теги не показываются в пользовательском selector и не перезаписываются.

Можно создать тег из операции, выбрать несколько, искать, переименовать,
перекрасить, удалить, открыть его операции. Удаление снимает тег также в корзине,
не удаляет операции; устаревший import/undo не восстанавливает удалённый тег.
Поиск журнала учитывает названия пользовательских тегов; есть отдельный фильтр.
AI JSON export сохраняет свой прежний allowlist и не раскрывает служебные теги.

## UI

- «Все операции» → отдельная кнопка «Категории» и фильтр тегов.
- В каждой строке `⋯`: категория, тег, редактирование, существующая корзина.
- Подробности операции: интерактивная категория, теги, применимое правило.
- «Настройки» → «Категории и теги», две вкладки.
- Selector категории с поиском и созданием используется также ручным вводом,
  редактором запланированных расходов и импортом чека.
- Использованы текущие тема, иконки и Material-компоненты Qesto; новый дизайн-язык
  не вводился. Проверены ширины 360/1200 и обе темы с реальными bundled fonts.

## Migration

Версия контейнера `UserFinancialDataCodec`: 6 → 7. Старые профили читаются с
пустыми classification settings; existing canonical assignments не переписываются
миграцией. Формат Synoball transaction, банковские API и формат импорта не менялись.
Настройки сохраняются вместе с текущим зашифрованным профилем. Старый build не
читает schema 7: откат после сохранения требует восстановления matching backup,
а не только замены exe.

## Known limitations

- Это локальные правила профиля, не облачная синхронизация между устройствами.
- Неизвестные варианты имени не угадываются; используются текущие aliases
  normalizer. Определение нового merchant alias — отдельная задача.
- При смене/удалении правила индивидуальные ручные назначения не отменяются.
- Массовое объединение не имеет обратной кнопки; доступны предварительное
  подтверждение и резервная копия. Корзина операций остаётся восстановимой.
- Суммы менеджера относятся к месяцу referenceDate профиля, а не произвольному
  аналитическому диапазону; межвалютные суммы не складываются.
- Реальный банковский сеанс не открывался, пользовательские операции не
  перекатегоризировались ради теста. Android проверен общими widget-тестами;
  физический телефон и новая установка APK в эту задачу не входили.
- AI-команды, splits, nested categories, сложные rule builders не добавлялись.
