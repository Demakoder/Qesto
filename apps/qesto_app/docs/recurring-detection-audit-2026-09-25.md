# Регулярные расходы: аудит и исправления, 25.09.2026

## Статус и границы результата

Исправлен существующий `EnrichmentEngine`, не создан второй детектор.
Формат Synoball / RecurringStream, API банков и импорт не менялись.
Исходные операции, счета, остатки, evidence и пользовательские правки не
перезаписывались. Новый расчёт меняет только производные recurring-признаки.

**Распознавание именно пользовательских Яндекс Плюса и ChatGPT пока НЕ доказано.**
В доступном локальном снимке 242 операции, даты 04.08–24.09.2026. Ни среди
канонических записей, ни среди candidates нет явных названий этих сервисов.
Прямой поиск проверял merchantName, normalizedDescription и rawDescription.
Подставлять произвольного посредника вместо ChatGPT нельзя. Пользователю задан
вопрос о названии продавца либо дате/сумме обоих платежей. Для окончательной
приёмки пунктов 1, 2 и 4 ТЗ нужно идентифицировать реальные записи и, при
необходимости, загрузить более длинную историю. Синтетические fixtures не
выдаются за реальные платежи пользователя.

## 1. Repository Analysis: существующий путь данных

1. Банковский сайт: SberExtractors → SberSyncSnapshot →
   BudgetController.importSberSnapshot / importStatement → StatementAdapter.
   Другие источники используют свои адаптеры того же SynoballCore.
2. Adapter возвращает кандидаты с merchant, описанием, датой, валютой, направлением,
   account и tags. Pending/review не превращаются в подтверждённый расход автоматически.
3. SynoballCore выполняет reconciliation/dedup, хранит raw/candidates/evidence и
   вызывает EnrichmentEngine.enrich для канонической операции.
4. `_refreshDerivedData` передаёт **всю каноническую историю**, без окна 60/90 дней,
   в `EnrichmentEngine.detectRecurring`. После импорта, редактирования, удаления
   и восстановления обновляются recurringStreams и isRecurring/recurringStreamId.
5. SynoballState сериализует потоки вместе с транзакциями; API v1 возвращает их
   с фильтром entityId. QestoReadModel переносит isRecurring в BudgetTransaction.
6. DesktopRecurringPage получает recurringStreams напрямую и слушает controller.
   Общий мобильный интерфейс тоже использует эту страницу. Статистический раздел
   раньше получал список ближайших **только** из upcomingExpenses, не из Synoball.

До исправления:

- фильтр только posted + outflow + непустой merchant;
- ключ группы: entity + нормализованное имя + **точная сумма в копейках** + валюта;
- minimum = 3; вся серия должна иметь интервалы 25–35 либо 6–8 дней;
- только monthly/weekly, хотя enum также содержит quarterly/yearly/irregular;
- category, description, MCC, source/account и merchantId не являются сигналами
  периодичности; descriptions лишь могут послужить источником merchant при enrichment;
- фиксированная confidence 0.92/0.88 независимо от числа наблюдений и качества;
- новый экземпляр core загружал старый кеш recurringStreams без пересчёта.

## 2. Diagnosis: воспроизведение ДО изменения алгоритма

Сначала запущен старый код на локальном снимке и обезличенных примерах ТЗ.

| Пример | Старый результат | Точная причина |
| --- | --- | --- |
| A: 499 × 4, ежемесячно | 1 серия | работает |
| B: 05.01 / 04.02 / 06.03 / 05.04 | 1 серия | допуск 25–35 уже достаточен |
| C: 399 / 399 / 449 / 449 | 0 | два ключа по сумме, в каждом только 2 записи |
| D: 2048 / 2112 / 2074 / 2151 | 0 | четыре ключа, по одному наблюдению |
| E: YANDEX*PLUS / YM*YANDEX PLUS / Яндекс Плюс / Yandex.Plus | 0 | prefix/алфавит разбивают группу |
| F: январь / февраль / апрель / май | 0 | один интервал >35 отвергает всю серию |
| Загруженный старый пустой кеш | остаётся пустым | пересчёт только после мутации/импорта |
| Найденная серия в старой статистике | нет в «Ближайших» | UI читает другую коллекцию |

Локальный старый расчёт воспроизвёл единственную сохранённую weekly-серию:
три перевода по 23 ₽ одному получателю. Но у этого же получателя **48 внешних
списаний с 31 разной суммой**. Старое разбиение по точной сумме вырезало удобный
поднабор из нерегулярной активности. Это свидетельство риска false positive,
а не доказанная подписка или обязательство. Имя получателя в отчёт не включено.

## 3. Implementation Plan и выполненное исправление

### Алгоритм (`lib/synoball/enrichment/enrichment.dart`)

- Группировка entity + merchant + currency, без суммы в ключе. Вся группа
  проверяется целиком; случайные регулярные поднаборы супермаркета не выбираются.
- Пунктуация нормализуется как раньше. Каталог merchant aliases дополнен узким
  соответствием вариантов Яндекс Плюса, включая YM prefix. Это **не whitelist
  подписок**: один платёж Яндекс Плюса не становится recurring. Неизвестный сервис
  проходит те же проверки; остальные сервисы Яндекса с Плюсом не объединяются.
- Сумма может меняться: проверяется диапазон (max/min ≤ 1.6), а не равенство;
  amountScore учитывает разброс относительно медианы. Резкое изменение больше
  диапазона оставлено ограничением, а не считается подтверждённым тарифом.
- Calendar cadence: weekly ±1 день, monthly ±4 дня, quarterly ±7, yearly ±14.
  Дни сравниваются по календарным датам, без ошибки усечения часов или DST.
- Пропуск одного периода допускается начиная с четырёх наблюдений. Требуется
  хотя бы один прямой интервал и coverage ≥0.65; произвольные редкие события не
  подгоняются под кратные недели. Confidence уменьшается при пропусках.
- Confidence = 0.96 × (0.45 intervalScore + 0.20 amountScore +
  0.20 min(n/4,1) + 0.15 coverage). Это эвристическая оценка, **не статистически
  откалиброванная вероятность подписки**.
- Два месячных наблюдения дают только предварительный прогноз, confidence ≤0.70.
  Двух недельных/квартальных/годовых наблюдений недостаточно. Слабые паттерны
  ниже 0.65 не показываются.
- TypicalAmount — последняя наблюдавшаяся цена, прогноз не создаёт новую операцию.
  ID серии не зависит от суммы, поэтому изменение тарифа не меняет его.
- Исключаются pending/reversed/deleted, not-observed, inflow, нулевые суммы,
  refunds, доказанные внутренние переводы, loyalty-only/non-cash, инвестиции,
  Excel-агрегаты за период, помеченные потенциальные дубли и неподтверждённые записи.
  **Внешний перевод продавцу/арендодателю не исключается просто из-за transferDirection.**
- Повтор одного canonical ID не увеличивает число наблюдений. Разные ID в один
  день не сливаются: такой неоднозначный паттерн консервативно отвергается.
- Опциональный `onDiagnostic` выдаёт локальный номер группы, число наблюдений,
  оценки и reason. Имена, account IDs, descriptions/credentials туда не входят;
  автоматического production logging нет.

### Сохранение и потребители

- `lib/synoball/core/synoball_core.dart`: при восстановлении пересчитываются
  производные серии. Финансовые поля и updatedAt операций остаются прежними.
- `lib/synoball/core/models.dart`: добавлен вычисляемый getter `isTentative`
  (меньше 3 наблюдений или confidence <0.8), **JSON-схема не изменена**.
- `lib/synoball/intelligence/financial_state.dart` и
  `lib/features/capital/domain/account_capital_service.dart`: предварительные
  серии не увеличивают обязательные расходы / резерв денег.
- `lib/desktop/pages/desktop_recurring_page.dart`: фильтр владельца, отдельная
  подпись предварительного прогноза, объяснение необходимого объёма истории.
- `lib/features/statistics/presentation/sections/secondary_statistics_sections.dart`:
  ближайшие серии берутся и из Synoball. Сумма за произвольный выбранный период
  больше не называется месячной и не умножается на 12 как доказанный годовой расход.
- `lib/synoball/ai/context.dart`: subscriptionAnalysis явно отмечает, что это
  непроверенные recurring patterns, а не подтверждённые подписки.

## 6. Ограничения и предложения, НЕ внедрённые без отдельного решения

- Регулярность ≠ подписка ≠ обязательство. Текущая модель не хранит отдельный
  подтверждённый пользователем договор. Еженедельный кофе может быть устойчивым
  поведенческим паттерном. Назвать его подпиской только по датам нельзя.
- Отдельным этапом: `patternKind` (subscription / obligation / habit / unknown),
  user-confirmed статус, exclude/dismiss, lifecycle active/paused/ended и версия
  detector. Нужна согласованная миграция модели/резервирования/API, сейчас не сделана.
- Биweekly отсутствует в enum. Не маскируется под weekly/irregular; добавить
  корректно вместе с моделью частоты и всеми потребителями в следующем этапе.
- Разные подписки/разовые покупки у общего агрегатора, отсутствующий merchant,
  переименование неизвестного посредника, огромная смена цены, возврат через
  другую валюту и длинные пропуски требуют дополнительных признаков/подтверждения.
  Не угадываем фактический сервис по одному названию платёжной площадки.
- Старые серии остаются историческими; nextExpectedAt не бесконечно переносится
  вперёд, имитируя новую оплату. Для прекращения/паузы нужен lifecycle.
- Confidence не доказывает юридическое обязательство. Существующая оценка
  mandatoryExpenses для устойчивых серий по-прежнему приблизительна; полноценный
  месячный эквивалент разных частот и подтверждение обязательств — отдельная работа.
- Неизвестные дубли под разными ID не объединяются этим детектором. Подлинность
  устанавливает существующий reconciliation; повтор в пределах одного дня не
  наращивает confidence. Оставшаяся неоднозначность дублей не скрывается.
