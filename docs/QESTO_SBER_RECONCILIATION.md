Число операций и итоговые суммы проверены по напечатанным банковским контролям, не только по результатам собственного парсера. Банковский профиль, PIN, cookies, установленное приложение и реальные финансовые данные не изменялись. EXE не собирался, Git push не выполнялся.

PDF и HTML **не являются взаимозаменяемыми полными выборками**. PDF относится к одному счёту; HTML содержит операции нескольких счетов и перевод между своими счетами. Видимый временной диапазон HTML также уже периода PDF. Дата операции и дата банковской обработки различаются. Возврат может быть отдельной строкой на сайте, но уменьшать исходную покупку в PDF. ## Исправления причин, не подгонка итогов

1. **Копейки суммы.** Точный DOM-текст имеет приоритет над старым округлённым `amountValue`; JS больше не округляет сумму операции до рублей. При объединении фактов связанной карты и счёта сохраняется `exactBalanceMinor`.
2. **Баланс/комиссия вместо суммы.** DOM-экстрактор исключает подписанные остатки и комиссии из кандидатов основной суммы. Для структурированной строки Dart не подставляет произвольное число из общего текста, если сумма не загрузилась. Старый неструктурированный текстовый формат остаётся поддержанным. Это ограниченные правила, а не доказательство поддержки любой будущей вёрстки банка.
3. **Бонусы при неполной загрузке.** Покупка без загруженной суммы, но с inline-бонусами не считается чисто бонусной записью. Для исключения бонусной операции нужны явные признаки начисления/списания бонусов. Неденежные записи не превращают показанный рядом баланс в покупку.
4. **Независимость смысла от подписи.** Новый веб-импорт помечает источник классификации `sber-classification:v2`. Слой исправления старых данных больше не переопределяет этот результат по сокращённому merchant/description. Отдельный тест воспроизводит внутренний перевод с подписью только «Платёжный счёт», проверяет Cash Flow, восстановление controller и повторный импорт. Для старых записей без маркера прежнее исправление ошибочно внутренних внешних переводов сохранено. Маркер не является новым полем канонической схемы и не отменяет field-level защиту пользовательских правок.
5. **Наблюдаемость.** `SberHistoryRowOutcome` различает принятую строку, выход за период, бонусы, служебную запись, отсутствие текста, даты или денежной суммы. Неполные строки не отбрасываются молча в JS. Ошибки чтения отражаются в отчёте и существующем partial-flow. На десктопе причины можно развернуть; отображается дата, если она распознана.
6. **Повторные наблюдения.** Если строка сначала не загрузилась, а затем прочиталась, прежняя ошибка исчезает. Временное исчезновение текста уже прочитанной строки не создаёт новую ошибку. Выход за выбранный период не считается поломкой парсера. Сообщение об неизвестном конце истории больше не утверждает без доказательств, что кнопка «Показать ещё» точно видна.

## Что остаётся открытым

- Нужны выписки по остальным участвующим счетам за один и тот же период и актуальные read-only наблюдения CEF. У пользователя запрошена вторая выписка; наличие HTML всех операций не доказывает account ownership каждой строки.
- Полная сверка покрытия живого scroll/load-more, остановка на выбранной границе, сохранение coverage/cursor между запусками ещё не подтверждены этим корпусом.
- Старые Sber IDs/fingerprints, PDF↔web account aliases, matched transfer legs, комиссии и возврат как отдельное событие против net-представления PDF требуют отдельных правил и тестов. Они не подменены ручной корректировкой Cash Flow.
- Старые округлённые/неполные данные не исправлялись напрямую в хранилище. Для обновления понадобятся новая сборка и повторная синхронизация; совместимость с legacy IDs требует дальнейшего контроля.
- Текущее Cash Flow за период нельзя приравнивать к текущему остатку всех счетов без совпадения периода/охвата и начальных остатков. Здесь не заявлено исправление всех предыдущих live-расхождений или готовность production-релиза.
