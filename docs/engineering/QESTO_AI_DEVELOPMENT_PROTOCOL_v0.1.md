# QESTO AI Development Protocol v0.1

## Назначение

Этот документ задаёт единый стандарт постановки задач и работы с AI-разработчиками (в первую очередь Codex) в проекте Qesto.

Цель протокола — ускорять разработку с помощью ИИ без потери архитектурной управляемости, качества, безопасности и понимания кодовой базы.

Документ основан на практиках Spec-Driven Development, AI-Driven Development, агентного инжиниринга, Human-in-the-Loop, Context Engineering и AI-SDLC, описанных в исследовании Ассоциации ФинТех «ИИ-трансформация разработки, 2026», и адаптирован под Qesto.

---

# 1. Базовый принцип

Qesto не должен разрабатываться в режиме бесконтрольного vibe-coding.

Для существенных задач применяется схема:

**Intent → Specification → Repository Analysis → Implementation Plan → Implementation → Tests → Review → Human Approval → Staging → Production**

ИИ является исполнителем и помощником, но не окончательным владельцем архитектурных и продуктовых решений.

Человек сохраняет ответственность за:

- продуктовый замысел;
- архитектурные решения;
- критерии качества;
- безопасность;
- принятие существенных изменений;
- выпуск в production.

---

# 2. Спецификация — основной источник истины

Для средних и крупных задач разработка должна начинаться со спецификации, а не с написания кода.

Спецификация должна описывать прежде всего ожидаемое поведение системы, а не конкретный способ реализации, если архитектурный способ заранее не принципиален.

Пример плохой постановки:

> Добавь вкладку целей.

Пример правильной постановки:

> Пользователь может создать финансовую цель, указать сумму и срок, видеть текущий прогресс, редактировать и удалять цель. Данные сохраняются между сессиями и используют существующую финансовую модель Qesto без создания параллельного источника истины.

Код является производным результатом спецификации.

---

# 3. Перед изменением кода Codex обязан изучить репозиторий

Перед реализацией существенной задачи AI-разработчик должен:

1. Найти существующую реализацию связанных функций.
2. Определить используемые модели данных.
3. Найти существующие API, сервисы, адаптеры, хуки, компоненты и утилиты.
4. Проверить текущие архитектурные правила.
5. Найти существующие тесты.
6. Определить, какие части системы будут затронуты.
7. Проверить, не существует ли уже частичной реализации задачи.
8. Не создавать дублирующую архитектуру, если нужный механизм уже существует.

Правило:

**Сначала понять существующую систему, потом менять её.**

---

# 4. Структура хорошего ТЗ для Codex

Для средней или крупной задачи ТЗ должно по возможности содержать следующие блоки.

## 4.1. Контекст

- где находится функция в Qesto;
- зачем она нужна пользователю;
- с какими существующими модулями связана;
- какие ранее принятые решения важно учитывать.

## 4.2. Целевой результат

Однозначное описание состояния системы после завершения задачи.

## 4.3. Функциональные требования

Что пользователь и система должны уметь после реализации.

## 4.4. Архитектурные ограничения

Какие существующие слои, сервисы, модели или API должны использоваться.

## 4.5. Что не делать

Явно фиксируются запрещённые или нежелательные действия.

## 4.6. Данные и миграции

Если задача затрагивает БД, необходимо определить влияние на существующие данные и схему.

## 4.7. Edge cases

Пограничные состояния и нетипичные сценарии.

## 4.8. UI-состояния

Если применимо:

- loading;
- empty;
- populated;
- error;
- partial data;
- offline;
- stale data.

## 4.9. Acceptance Criteria

Проверяемые критерии, по которым можно однозначно определить, выполнена задача или нет.

## 4.10. Тестирование

Что необходимо проверить автоматически и вручную.

## 4.11. Security / Privacy

Какие требования безопасности и приватности применимы.

## 4.12. Финальный отчёт

Что Codex обязан сообщить после реализации.

---

# 5. Обязательные ограничения по умолчанию

Если в конкретном ТЗ не указано обратное, Codex должен соблюдать следующие правила.

## Архитектура

- Не создавать второй источник истины.
- Не дублировать существующие сервисы и модели.
- Не вводить параллельную архитектуру для уже существующего процесса.
- Не проводить крупный рефакторинг несвязанных частей проекта.
- Не менять публичные API без необходимости.
- Не менять архитектурные контракты без явного обоснования.
- Не добавлять новую зависимость, если задача разумно решается существующим стеком.
- Не создавать временные костыли как постоянную архитектуру.

## Совместимость

- Не ломать существующие пользовательские сценарии.
- Сохранять обратную совместимость там, где она необходима.
- Существующие данные пользователя не должны теряться.

## Реализация

- Не заменять существующий рабочий backend mock-данными.
- Не оставлять критически важную бизнес-логику только на клиенте, если она должна быть серверной.
- Не скрывать ошибки пустыми catch-блоками или молчаливыми fallback-механизмами.
- Не считать задачу завершённой только потому, что код компилируется.

---

# 6. Работа с данными и миграциями

Для задач, затрагивающих БД:

1. Сначала изучить существующую схему.
2. Максимально переиспользовать существующие сущности.
3. Не дублировать данные без необходимости.
4. Миграции должны быть безопасными и предсказуемыми.
5. По возможности миграции должны быть обратимыми.
6. Не выполнять destructive operations над production-данными автономно.
7. Перед потенциально опасными изменениями предусматривать резервное копирование или безопасный план отката.
8. Не удалять или преобразовывать пользовательские данные без явной необходимости и проверки.
9. При изменении структуры учитывать старые записи и существующих пользователей.

---

# 7. Human-in-the-Loop

ИИ не должен самостоятельно принимать окончательные решения в критичных точках разработки.

Человеческое подтверждение требуется как минимум для:

- существенных архитектурных изменений;
- destructive database migrations;
- изменения механизмов аутентификации и авторизации;
- изменения финансовой бизнес-логики;
- изменения правил расчётов;
- операций с production;
- изменения доступа к пользовательским данным;
- подключения новых внешних провайдеров данных;
- передачи данных во внешние сервисы;
- отключения или ослабления security-проверок.

---

# 8. Production должен быть защищён от автономных действий агентов

AI-разработчик не должен иметь возможность бесконтрольно изменять production.

Целевая модель:

**Development → Tests → Review → Staging → Human Approval → Production**

Рекомендуемые правила:

- отдельные dev/staging/prod окружения;
- отдельные credentials;
- принцип least privilege;
- запрет прямых destructive-команд в production;
- production-секреты недоступны агенту без необходимости;
- миграции проходят отдельную проверку;
- опасные операции требуют подтверждения человека;
- действия должны быть журналируемыми и проверяемыми.

---

# 9. Безопасность и приватность Qesto

Qesto работает с чувствительными финансовыми данными, поэтому безопасность имеет приоритет над скоростью разработки.

По умолчанию:

- использовать least privilege;
- не хранить секреты в исходном коде;
- не добавлять credentials в репозиторий;
- не выводить секреты в логи;
- не логировать чувствительные финансовые данные без необходимости;
- не отправлять пользовательские финансовые данные сторонним сервисам без явной необходимости и согласованной архитектуры;
- учитывать существующую систему authentication/authorization;
- не ослаблять проверки безопасности ради упрощения реализации;
- проверять права доступа на серверной стороне;
- не доверять данным клиента;
- валидировать входные данные;
- учитывать возможность повторных запросов, дублей и race conditions;
- для финансовых операций и вычислений избегать неявного поведения.

---

# 10. Тестирование — часть реализации, а не отдельная необязательная стадия

Рост количества AI-генерированного кода делает тестирование и review ключевым узким местом разработки.

После реализации Codex должен, если применимо:

1. Запустить существующие тесты.
2. Добавить тесты для новой бизнес-логики.
3. Проверить regression связанных сценариев.
4. Запустить typecheck.
5. Запустить lint.
6. Проверить build.
7. Проверить миграции.
8. Проверить критические edge cases.
9. Проверить ошибки и негативные сценарии.
10. Указать, какие проверки невозможно выполнить автоматически.

Новая функциональность без проверки не считается полностью завершённой.

---

# 11. Acceptance Criteria обязательны для существенных задач

Acceptance Criteria должны быть конкретными и проверяемыми.

Плохой критерий:

> Вкладка должна хорошо работать.

Хорошие критерии:

- пользователь может создать цель;
- после перезапуска приложения цель сохраняется;
- прогресс рассчитывается корректно;
- редактирование не создаёт дубликат;
- удаление цели удаляет только выбранную цель;
- пустое состояние отображается корректно;
- ошибка API отображается без падения интерфейса;
- существующие тесты проходят;
- новая логика покрыта тестами;
- существующий финансовый расчёт не изменился.

---

# 12. Edge cases должны продумываться заранее

Для каждой средней и крупной функции необходимо подумать о нетипичных сценариях.

Примеры для Qesto:

- нет данных;
- данные частичные;
- данные устарели;
- значение равно нулю;
- отрицательная сумма;
- неизвестная категория;
- неизвестный счёт;
- удалённый источник данных;
- повторно импортированная операция;
- дубликат транзакции;
- конфликт между несколькими источниками;
- пользователь вручную изменил автоматически полученные данные;
- сеть недоступна;
- API отвечает медленно;
- API возвращает ошибку;
- авторизация истекла;
- синхронизация выполняется параллельно;
- пользователь закрыл приложение во время операции.

---

# 13. Контекст важнее длинных промптов

Вместо постоянного повторения архитектуры Qesto в каждом ТЗ необходимо постепенно формировать постоянный машинно-читаемый контекст проекта.

Предпочтительно хранить в репозитории:

- архитектурное описание Qesto;
- ключевые модели данных;
- правила Synoball;
- правила импорта и дедупликации;
- финансовые правила и определения;
- правила API;
- security requirements;
- UI/UX conventions;
- naming conventions;
- правила тестирования;
- инструкции по миграциям;
- описание окружений;
- правила работы с внешними банковскими источниками;
- требования к логированию и observability.

AI-разработчик должен использовать этот контекст как источник истины и не переизобретать правила в каждой задаче.

---

# 14. AI Skills для повторяющихся задач

Повторяющиеся процессы разработки желательно превращать в переиспользуемые инструкции/skills.

Потенциальные Qesto Skills:

## Feature Development Skill

Стандартная процедура добавления новой продуктовой функции.

## Transaction Pipeline Skill

Правила изменения цепочки:

source → adapter → normalization → deduplication → transaction → storage → UI.

## Bank Import Skill

Правила добавления или изменения банковских источников.

## Database Migration Skill

Проверка схемы, миграции, совместимости и отката.

## Security Review Skill

Проверка auth, permissions, secrets, input validation, external data transfer и sensitive logs.

## Regression Review Skill

Поиск связанных сценариев, которые могли быть затронуты изменением.

## UI Screen Skill

Проверка loading/empty/error/populated states и соответствия существующим компонентам.

## Incident Analysis Skill

Анализ логов, trace/request IDs, адаптеров, ошибок синхронизации и причин расхождения данных.

Skills должны быть версионируемыми и изменяться вместе с архитектурой Qesto.

---

# 15. Многоагентная разработка

Полноценная сложная multi-agent инфраструктура не является обязательной на ранней стадии Qesto.

Однако логическое разделение ролей полезно уже сейчас.

Базовая схема:

### Agent 1 — Implementer

Изучает задачу и реализует изменение.

### Agent 2 — Test / QA Reviewer

Проверяет реализацию, тесты и edge cases.

### Agent 3 — Architecture / Security Reviewer

Ищет архитектурные нарушения, security-проблемы, дублирование и технический долг.

### Human

Принимает или отклоняет результат.

В дальнейшем возможна схема:

**Orchestrator → Implementer → Test Agent → Security Agent → Review Agent → Human Approval**

Но автоматизация не должна становиться самоцелью.

---

# 16. Не строить инфраструктуру ради инфраструктуры

Qesto — продукт, а не исследовательская AI-платформа.

Поэтому не следует преждевременно создавать:

- сложный собственный Agent Runtime;
- огромную оркестрационную платформу;
- десятки специализированных агентов;
- сложный LLMOps-контур без реальной необходимости;
- инфраструктуру, стоимость поддержки которой выше создаваемой пользы.

Сначала должны быть качественно выстроены:

1. спецификации;
2. контекст проекта;
3. тесты;
4. review;
5. security;
6. staging;
7. production discipline.

Только после этого имеет смысл увеличивать автономность агентов.

---

# 17. Контроль технического долга

Главная опасность AI-разработки — не только ошибочный код, а способность генерировать огромный объём изменений быстрее, чем человек способен их осмыслить.

Поэтому Codex должен предпочитать:

- небольшие понятные изменения;
- переиспользование существующих механизмов;
- простую архитектуру;
- ясные зависимости;
- хорошо тестируемую бизнес-логику;
- решения, понятные следующему разработчику.

Следует избегать:

- чрезмерных abstraction layers;
- ненужных wrapper-ов;
- скрытой магии;
- большого рефакторинга без необходимости;
- множества почти одинаковых сервисов;
- трудно отслеживаемых side effects;
- кода, работа которого нельзя объяснить.

Если AI-разработчик не может кратко объяснить архитектуру внесённого изменения, изменение требует дополнительного review.

---

# 18. Размер ТЗ должен соответствовать размеру задачи

Протокол не должен создавать бюрократию.

## Маленькая задача

Например:

- исправить отступ;
- изменить текст;
- исправить локальную UI-ошибку.

Достаточно короткой инструкции и проверки результата.

## Средняя задача

Например:

- добавить новый экран;
- изменить бизнес-логику существующей функции;
- добавить API endpoint;
- добавить новый тип импорта.

Нужна компактная спецификация, ограничения, edge cases и acceptance criteria.

## Крупная задача

Например:

- банковская интеграция;
- инвестиционный модуль;
- семейные финансы;
- AI-агент;
- новая финансовая модель;
- изменение архитектуры синхронизации.

Нужна полноценная Spec-Driven спецификация с архитектурой, данными, безопасностью, тестами и планом внедрения.

---

# 19. Финальный отчёт Codex

После выполнения существенной задачи Codex должен кратко сообщить:

1. Что реализовано.
2. Какие файлы были изменены.
3. Какие новые файлы были созданы.
4. Какие архитектурные решения были приняты.
5. Были ли изменены модели данных.
6. Есть ли миграции.
7. Какие тесты были добавлены.
8. Какие проверки были запущены.
9. Какие проверки прошли/не прошли.
10. Что невозможно было проверить автоматически.
11. Есть ли известные ограничения.
12. Есть ли потенциальный технический долг.
13. Что необходимо проверить вручную.

Не следует писать длинный отчёт ради отчёта — важна проверяемость результата.

# 21. Целевая модель разработки Qesto

На текущем этапе:

**Product Intent**
↓

# 22. Главный критерий

Использование ИИ в разработке Qesto считается успешным не тогда, когда ИИ написал больше кода, а когда Qesto быстрее развивается при одновременном сохранении:

- понятной архитектуры;
- корректности финансовой логики;
- безопасности пользовательских данных;
- тестируемости;
- управляемости изменений;
- низкого технического долга;
- способности команды понимать и развивать кодовую базу дальше.

**Скорость без управляемости не является преимуществом.**
