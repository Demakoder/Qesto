# Synoball Core: подробный разбор кода

Этот документ описывает не интерфейс Flutter, а финансовое ядро, которым
пользуются Android, Windows и Web-версия Qesto. Платформенные экраны и способы
получения файла или уведомления разные, но после адаптера данные проходят один
и тот же путь Synoball.

## 1. Главная идея

Synoball отделяет исходное наблюдение от финансового факта:

```text
уведомление / выписка / чек / голос / ручной ввод
                         │
                         ▼
                       adapter
                         │
       RawPayload + IngestionRecord + TransactionCandidate
                         │
                         ▼
        deduplication + source trust + enrichment
                         │
                         ▼
          CanonicalTransaction + SourceEvidence
                         │
                         ▼
         recurring streams + read models + Qesto UI
```

- `RawPayload` хранит исходный текст или представление входных данных. Он нужен
  для диагностики и повторного разбора.
- `IngestionRecord` описывает одну попытку импорта: источник, адаптер, статус и
  ошибку.
- `TransactionCandidate` — ещё не окончательная операция, а предложение
  адаптера.
- `CanonicalTransaction` — единая операция, которую показывают бюджет и
  статистика.
- `SourceEvidence` связывает canonical transaction с каждым источником,
  подтвердившим эту операцию. Поэтому чек, push и строка выписки не обязаны
  превращаться в три расхода.

## 2. Где находится код

- `apps/qesto_app/lib/synoball/core/models.dart` — модели и JSON-сериализация.
- `apps/qesto_app/lib/synoball/core/synoball_core.dart` — состояние и команды
  ядра.
- `apps/qesto_app/lib/synoball/ingestion/adapter.dart` — общий контракт
  адаптера.
- `apps/qesto_app/lib/synoball/adapters/` — адаптеры ручного ввода, голоса,
  Android-уведомлений, чеков, выписок и legacy-данных.
- `apps/qesto_app/lib/synoball/reconciliation/deduplication.dart` — поиск уже
  существующей операции.
- `apps/qesto_app/lib/synoball/reconciliation/source_trust_policy.dart` —
  правило, какой источник имеет право заменить поля операции.
- `apps/qesto_app/lib/synoball/enrichment/enrichment.dart` — нормализация
  магазина, категории и периодических платежей.
- `apps/qesto_app/lib/synoball/analytics/` — read models для интерфейса и
  статистики.

## 3. `SynoballCore`: состояние и индексы

### Конструктор `SynoballCore`

Конструктор получает `SynoballState`. При обычном запуске он пустой, а после
перезапуска приложения содержит восстановленные из JSON данные. Все списки
копируются через `List.of`, поэтому ядро не изменяет переданный объект снаружи.

После копирования строятся внутренние индексы:

- `_transactionIndexById`: transaction id → позиция в `_transactions`;
- `_candidateIndexById`: candidate id → позиция в `_candidates`;
- `_ingestionRecordIndexById`: ingestion id → позиция в
  `_ingestionRecords`;
- `_importBatchIndexById`: batch id → позиция в `_importBatches`;
- `_evidenceByTransactionId`: transaction id → evidence этой операции;
- `_providerTransactionIds`: множество всех внешних provider id;
- `_providerEvidenceKeys`: тройка transaction/source/provider id для быстрой
  проверки повторного evidence.

Списки остаются источником истины и сохраняются в прежнем JSON-формате.
Индексы — только производный слой в памяти, поэтому миграция пользовательских
данных не нужна.

### Getter `state`

Возвращает снимок `SynoballState`. `List.unmodifiable` не позволяет экрану или
сервису случайно изменить внутренние коллекции ядра. Сериализовать и хранить
следует именно этот снимок.

### Getter `transactions`

Фильтрует soft-deleted операции. Удалённая операция остаётся в полном state,
но не попадает в бюджет и обычный интерфейс.

### Getter `pendingCandidates`

Возвращает кандидатов со статусом `pending`. Например, голосовая команда
создаёт именно такой кандидат, пока пользователь её не подтвердил.

### `transactionById(id)`

Берёт позицию из `_transactionIndexById` и читает элемент списка. Раньше метод
перебирал весь список. Сложность поиска изменилась с `O(T)` на среднюю `O(1)`,
где `T` — число транзакций.

### `hasTransactionOrProviderId(id)`

Сначала проверяет canonical id, затем `_providerTransactionIds`. Метод нужен,
когда внешний канал спрашивает, импортировалась ли операция ранее. Evidence
больше не сканируется целиком.

## 4. Полный путь `ingest(adapter, input)`

`ingest` — главная входная функция ядра.

1. `adapter.parse(input)` превращает платформенный формат в `AdapterResult`.
   Ядро ничего не знает о PDF, Android Notification API или распознавании речи.
2. `_upsertMany` добавляет либо обновляет учреждения, подключения, согласия и
   счета.
3. Raw payload, ingestion record и candidates сохраняются до дедупликации.
   Это важно: даже ошибочный кандидат остаётся диагностируемым.
4. Кандидаты с `requiresConfirmation == true` попадают в `pending` и пока не
   создают расход.
5. Каждый подтверждённый кандидат передаётся в `_reconcile`.
6. Ошибка одного кандидата увеличивает `failures`, но не откатывает успешно
   импортированные строки. Это partial-success модель для больших выписок.
7. Ingestion record получает `completed` либо `needsReview`. Import batch
   получает количества created/matched/failed.
8. `_refreshDerivedData` один раз пересчитывает периодические платежи для всей
   пачки.
9. `_emit` создаёт `financial_state.updated` и события состояния connection.
10. Метод возвращает `IngestionOutcome`: созданные, объединённые и ожидающие
    подтверждения id плюс предупреждения.

## 5. Команды пользователя

### `confirmCandidate(candidateId, actorId)`

Находит candidate и ingestion record по индексам. `candidate.copyWith`
повышает confidence до `1`, trust до `userConfirmed` и снимает требование
подтверждения. После `_reconcile` создаётся audit-запись с пользователем и
назначением действия.

### `upsertEntity` и `upsertAccount`

Вызывают общий `_upsertMany`. Если id новый — объект добавляется в конец; если
id уже есть — объект заменяется на прежней позиции. Порядок сериализации при
этом сохраняется.

### `removeAccountIfUnused(accountId)`

Удаляет счёт только тогда, когда на нём нет активных операций. Это защищает
ссылочную целостность старых транзакций.

### `updateTransaction(transaction, actorId)`

Находит операцию по индексу, ставит текущее `updatedAt` и доверие
`userConfirmed`, запускает enrichment только для изменённой операции, пишет
audit/event и пересчитывает recurring streams.

### `deleteTransaction(id, actorId)`

Это soft delete: статус становится `deleted`, а исходные данные и evidence
сохраняются. После удаления recurring-признаки пересчитываются, поэтому
разрушенная цепочка подписки больше не остаётся периодической.

### `restoreTransaction(transaction)`

Возвращает статус `posted`. Если операции уже нет в списке, добавляет её и
сразу дополняет индекс; иначе заменяет на прежней позиции.

## 6. `_reconcile`: как несколько источников становятся одной операцией

Функция сначала вызывает `TransactionDeduplicator.findMatch`.

Если совпадения нет:

1. canonical id берётся из кандидата либо формируется как `txn-{candidateId}`;
2. создаётся `CanonicalTransaction`;
3. `_enrichment.enrich` нормализует магазин и категорию;
4. операция и её индекс добавляются в память;
5. создаётся событие `transaction.created`.

Если совпадение есть:

1. текущая операция достаётся за `O(1)`;
2. из `_evidenceByTransactionId` берутся уже известные источники;
3. `SourceTrustPolicy.shouldReplace` решает, может ли новый источник заменить
   основные поля;
4. `_shouldReplaceOccurredAt` не позволяет дате проводки из выписки затереть
   точное время чека или push;
5. `_sourceDetailRank` выбирает более подробные merchant/description;
6. `_mergeCategory` не даёт общей категории `other` затереть точную;
7. теги объединяются как множество, поэтому дубликаты исчезают;
8. изменённая операция проходит enrichment и сохраняется;
9. создаётся событие `transaction.merged` со score и причинами совпадения.

После обеих веток `_providerEvidenceKeys` проверяет, не записано ли такое же
evidence. Новое evidence индексируется функцией `_indexEvidence`. Candidate
получает статус `confirmed` для новой операции или `merged` для найденной.

## 7. Дедупликация

### `findMatch`

Порядок проверок принципиален:

1. Из транзакций выбираются только активные операции того же entity и строится
   `activeById`.
2. Если пришёл `canonicalId`, это точное совпадение со score `1`.
3. Evidence одним проходом группируется по transaction id. Одновременно ищется
   совпадающий provider id в рамках того же source type.
4. Для `legacy`, `manual`, `manualVoice` и `modelInference` нечёткое слияние
   запрещено: две ручные покупки одинаковой суммы должны остаться разными.
5. Для остальных источников проверяется, что у операции ещё нет fuzzy evidence
   этого типа.
6. `_score` оценивает оставшиеся пары и возвращается лучший результат выше
   `defaultThreshold` (`0.84`).

До оптимизации evidence фильтровался заново для каждой транзакции, то есть один
кандидат мог требовать `O(T × E)`. Теперь evidence группируется одним проходом:
`O(T + E)` плюс собственно сравнение подходящих транзакций.

### `_score`

Сначала обязательны точное совпадение суммы в minor units, валюты и направления.
Затем:

- merchant similarity ниже `0.5` сразу отвергается;
- окно времени — 24 часа, либо 48 часов при участии выписки;
- базовые 0.6 даются за деньги/валюту/направление;
- до 0.2 — за магазин;
- до 0.2 — за близость времени;
- 0.04 — за одинаковый счёт.

Итог ограничивается диапазоном 0…1. В `reasons` сохраняется объяснение score —
оно попадает в событие merge и пригодно для диагностики.

### Нормализация магазина

`_merchantKey` приводит строку к нижнему регистру, заменяет `ё`, убирает формы
юрлица, города, длинные номера и лишние пробелы. Известные варианты вроде
`PYATEROCHKA` и `5ka` приводятся к одному ключу. RegExp теперь создаются один
раз на модуль, а не при каждом сравнении.

`_merchantSimilarity` берёт максимум из сходства множеств слов и
`_diceCoefficient`. Dice coefficient сравнивает пары соседних символов, поэтому
переживает небольшие опечатки и отличия транслитерации лучше точного равенства.

## 8. Enrichment и recurring streams

### `enrich(transaction)`

`_resolveMerchant` выбирает стабильные merchant id/name для известных сетей.
`_categoryFor` выводит категорию из магазина или provider category. Ручная
`userCategoryOverride` всегда имеет приоритет.

Enrichment больше не меняет `updatedAt`. Время изменения задаёт команда,
которая действительно изменила операцию. Поэтому импорт посторонней выписки не
делает вид, будто все старые расходы только что обновились.

### `detectRecurring(transactions)`

Функция:

1. берёт только `posted` outflow;
2. группирует по `(entityId, merchant, minorUnits, currency)`;
3. сортирует каждую группу по времени;
4. требует минимум три операции;
5. считает интервалы: 25–35 дней означают monthly, 6–8 — weekly;
6. создаёт `RecurringStream` и прогноз следующей даты.

`entityId` обязателен в ключе: одинаковые подписки двух пользователей больше
не смешиваются. Валюта входит и в ключ, и в stream id. `_sameTimeNextMonth`
корректно переводит 31 января в последний существующий день февраля и сохраняет
UTC/local тип даты и точное время.

### `_refreshDerivedData`

Перестраивает список recurring streams и map `transactionId → stream`. Затем
меняет только операции, чей recurring-флаг или stream id действительно
изменился. Если цепочка исчезла, `clearRecurringStreamId` явно записывает
`null`; обычный nullable `copyWith` не способен отличить «не менять поле» от
«очистить поле».

## 9. Вспомогательные функции и модели

### `_indexEvidence`

За один вызов обновляет все три evidence-индекса. Вызывать его нужно в каждой
ветке, которая добавляет `SourceEvidence`; иначе списки и индексы разойдутся.

### `_emit` и `_audit`

`_emit` описывает машинное событие для интерфейса или будущего event transport.
`_audit` описывает действие пользователя: кто, что, для какой entity и с какой
целью сделал. Это разные журналы и смешивать их не следует.

### `_buildPositionIndex`

Строит map id → индекс списка за `O(N)`. Он используется при запуске и внутри
универсального upsert.

### `_upsertMany`

Сначала один раз строит позиции существующих объектов, затем обрабатывает всю
входную коллекцию. Было `O(N × M)` из-за `indexWhere` для каждого объекта,
стало `O(N + M)`.

### `TransactionCandidate.copyWith`

Кроме status теперь умеет менять confidence, source trust и флаг подтверждения.
Это убрало ручное копирование всех полей при подтверждении голосовой операции.

### `CanonicalTransaction.copyWith`

Параметр `clearRecurringStreamId` решает типичную проблему nullable copyWith:
`null` обычно означает «оставить старое значение», поэтому для намеренной
очистки нужен отдельный явный флаг.

## 10. Что именно ускорилось

| Операция | Было | Стало |
|---|---:|---:|
| Поиск transaction/candidate/record/batch по id | `O(N)` | в среднем `O(1)` |
| Проверка provider id | `O(E)` | в среднем `O(1)` |
| Evidence одной операции | `O(E)` | `O(k)` |
| Подготовка fuzzy dedup одного кандидата | `O(T × E)` | `O(T + E)` |
| Upsert пачки справочников | `O(N × M)` | `O(N + M)` |
| Enrichment при общем refresh | все транзакции | только созданная/изменённая |

На локальном однопроходном тесте импорта 400 уникальных строк время ядра
уменьшилось с 224 до 68 мс, примерно в 3,3 раза. Это ориентир, а не обещание
фиксированного времени: результат зависит от процессора, режима Dart и данных.

## 11. Почему оптимизация не ломает хранение и платформы

- Публичные JSON-поля и версия `SynoballState` не изменены.
- Индексы не сериализуются и восстанавливаются конструктором после загрузки.
- Адаптерный контракт и `IngestionOutcome` не изменены.
- Android, Windows и Web вызывают то же ядро, поэтому исправления общие.
- Специфичные возможности остаются платформенными: Android читает push через
  системный notification listener, desktop/web этого делать не могут; зато PDF,
  чек и ручной ввод после parsing обрабатываются одинаково.

## 12. Проверки

Регрессионные тесты подтверждают:

- push, выписка и чек по-прежнему объединяются;
- две похожие реальные покупки не склеиваются;
- точное время чека не заменяется полуночью из выписки;
- voice candidate ждёт подтверждения;
- `updatedAt` старой операции не меняется от постороннего импорта;
- recurring-флаги очищаются после разрушения цепочки;
- recurring streams разных entity не смешиваются;
- JSON persistence сохраняет raw/canonical/evidence.

После изменений `flutter analyze` проходит без замечаний, целевые тесты ядра —
14/14, полный набор проекта — 219 успешных и 5 штатно пропущенных тестов.

## 13. Как защищаются данные ядра

Synoball не реализует собственную криптографию: его `SynoballState` входит в
единый `UserFinancialData` и сохраняется repository через защищённый слой. Это
позволяет ядру отвечать только за финансовые правила, а шифрование, Android
Keystore, ограничения входных файлов, сетевой контур и подпись сборок держать
на границах приложения.

Полный пофайловый разбор защиты, форматов AES-GCM, миграции старого plaintext и
остаточных рисков находится в
[`SECURITY_IMPLEMENTATION_RU.md`](SECURITY_IMPLEMENTATION_RU.md).
